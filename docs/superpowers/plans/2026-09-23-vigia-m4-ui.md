# Vigia M4: Dashboard, Mod Login and First-Run Setup

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The live dashboard from the spec: the Live, Uncertain, Highlights, Rules, Settings
and Stats tabs. It is served by the Vigia host and secured for both modes: local (desktop or
terminal) and exposed (a VPS with mods).

**Architecture:**
- `packages/server` gains an auth module, a JSON API, a dashboard WebSocket, an audit log
  and config mutations.
- `packages/ui` gains the dashboard app, built with Preact because tabs, forms and live
  lists outgrow vanilla DOM code. The overlay stays vanilla.

**Spec:** `docs/superpowers/specs/2026-09-23-vigia-design.md`

## Rulings made while planning

- **Auth modes.**
  - **Local** (bound to loopback): no login, and the user is the broadcaster (as in the
    spec).
  - **Exposed** (any other bind address): every page and API call needs a session. There
    are two ways in:
    1. **Admin code**: a random code printed in the server logs and stored in SQLite. It
       grants the broadcaster role. This is the spec's "setup code", and it also covers the
       read-only `observe` source, which has no Twitch identity.
    2. **Sign in with Twitch**: the implicit flow against `<origin>/auth/callback`, used only
       to learn who the user is. The token is validated (its `client_id` must be ours) and
       then discarded. The role is broadcaster when the user id matches, or moderator when
       the user is in the live moderator set.
- **Browser attacks on a local server.** Any website the streamer visits can try to talk to
  `127.0.0.1:7777`. So:
  - every state-changing API call requires the `X-Vigia: 1` header, which cross-site forms
    can't send and which triggers a CORS preflight we never approve;
  - the `Host` header must be a loopback name in local mode, against DNS rebinding;
  - dashboard WebSockets must come from our own `Origin`.
- **The wizard in M4 covers what the host itself owns:** language, packs and the
  anti-spoiler, the overlay URL, and a status check of Twitch and Jev. Entering the Twitch
  client ID, the device login and the Jev key needs somewhere safe to keep secrets, which
  is Electron's `safeStorage` (M5). In server mode those come from environment variables.
  The wizard shows them as read-only status.
- **Spoiler text** reaches dashboard clients flagged as `spoiler: true`, and the UI blurs it
  until clicked (as in the spec). **Protected topics** are only sent to the moderator role.
  The broadcaster role gets only the count.

## Global Constraints

- Everything in the M1–M3 constraints still holds.
- Sessions use an HttpOnly, SameSite=Lax cookie, Secure when served over HTTPS. Removing a
  moderator on Twitch ends that moderator's sessions at once.
- Mods can do everything except change keys, the Twitch connection or access settings.
  The broadcaster can do everything. Every manual action is audited with who did it.
- All user-visible UI strings are in `en` and `es`.

## Review Focus

1. **A cross-site POST to the local dashboard API** (no `X-Vigia` header) is rejected with
   403 (Task 2 test).
2. **A request with `Host: evil.example`** in local mode is rejected (Task 2 test).
3. **A WebSocket from a foreign `Origin`** is rejected (Task 4 test).
4. **The broadcaster role never receives protected topics**, over either the API or the WS
   (Task 4 test).
5. **A Twitch token issued for another app** (`client_id` mismatch) can't log in (Task 2
   test).

### Task 1: Store additions
- Decisions gain `author_id` and `resolved` (null, `applied` or `dismissed`), plus
  `decision(id)` and `resolve(id, how)`.
  - Uncertain entries are the unresolved rows.
- New `audit(ts, login, role, action, target, detail)` table, with `recordAudit` and
  `audit(limit)`.
- Tests for each.

### Task 2: Auth (`packages/server/src/auth.ts`)
`createAuth({ mode, adminCode, clientId?, broadcasterId?, validate? })` provides:
- `loginWithCode(code)`;
- `loginWithTwitch(token)`;
- `session(cookieHeader)`;
- `logout(id)`;
- `setModerators(ids)`, which drops sessions of removed mods;
- `guard(req, { write, role })`, returning `{ ok, status, user }`.

Tests cover:
- local mode is open, but `Host` is checked;
- writes need `X-Vigia`;
- a wrong admin code fails;
- a Twitch token whose `client_id` is not ours fails;
- the moderator and broadcaster roles are assigned correctly;
- a removed mod loses the session;
- sessions expire after 12 h.

### Task 3: Config mutations (`config-file.ts`)
`update(mutator(doc))` runs a mutation, validates it and writes the result, keeping
comments. It powers these helpers:
- `setRule(id, patch)` (enabled, act, unsure, action, seconds, progress);
- `addRule(rule)` and `removeRule(id)`;
- `setSettings(patch)` (language, highlights.*, exempt, observe);
- `replaceText(yaml)` for the raw editor.

Invalid results are rejected with the parser's errors and leave the file untouched.
Tests cover each helper and that comments survive.

### Task 4: API and dashboard WebSocket (`host.ts` → `api.ts`)
Routes. Reads need a session (any role); writes also need `X-Vigia`.
- `GET /api/me`, `POST /api/login/code`, `POST /api/login/twitch`, `POST /api/logout`.
- `GET /api/overview` returns the state, the config summary, the overlay URL and the auth
  mode.
- `GET /api/decisions?limit=`, `GET /api/uncertain`, and
  `POST /api/uncertain/:id/{apply,dismiss}`.
- `POST /api/actions`: delete, timeout, ban, highlight (from a decision) and announce.
- `POST /api/highlights/{clear,next}` and `GET /api/highlights`.
- `GET|PUT /api/config` (raw YAML), `PATCH /api/rules/:id`, `POST /api/rules`,
  `DELETE /api/rules/:id` and `PATCH /api/settings`.
- `POST /api/test` `{ text }` returns each rule's probability and band, without acting.
- `GET|PUT /api/topics`: mods only for the list. The broadcaster gets `{ count }`.
- `POST /api/state` (pause/resume, observe on/off).
- `GET /api/stats` returns messages per minute, actions, and tokens with the estimated
  $/hour. A `createUsageMeter()` is fed by the evaluator's `onUsage`.
- `GET /api/audit` (broadcaster only).
- WS `/ws/dashboard`: session and origin are checked, and it pushes `decision`, `state`,
  `highlight`, `warning` and `stats`.

Sources gain `moderators(ids)` and `identity` (`clientId`, `broadcasterId`) so Twitch login
works. Tests use real HTTP for:
- each route's role and CSRF rules;
- the topics redaction;
- the uncertain apply path;
- that the WS rejects a foreign origin;
- the audit rows.

### Task 5: Dashboard UI (`packages/ui`, Preact)
- `index.html` hosts the dashboard. `login.html` offers the admin code and Sign in with
  Twitch, and `/auth/callback` finishes the Twitch login.
- i18n in `src/i18n/{en,es}.json`.
- The tabs, as in the spec:
  - thresholds are re-evaluated on the client from stored probabilities;
  - spoiler rows are blurred until clicked;
  - a test box sits on each rule;
  - the raw YAML editor has inline errors.
- Visual QA uses Playwright screenshots against a running host.

### Task 6: First-run wizard (M4 scope, see rulings)
Shown until `setupDone` is set in SQLite. It walks through language, packs and the
anti-spoiler, the overlay URL with a preview, a status check (Twitch source connected and
Jev key working, via a test call), and explains observe mode.

### Task 7: CLI wiring
- The auth mode comes from `--host`.
- The admin code is printed on start.
- The usage meter is connected, and the dashboard URL is printed.
